# 개인정보 보유·삭제와 백업·복구 운영 초안

상태: **운영 검토 필요 / 실제 고객 데이터 반입 금지** (2026-09-28). 이 문서는 현재 구현에 맞춘 내부 실행 기준이다. 고객에게 고지할 보존기간이나 법정 보존기간의 확정, 실제 백업·복구 성공을 뜻하지 않는다. 책임자가 업무별 법적 근거와 기간을 확인하고 공개 고지·위탁 계약을 정리해야 운영 기준으로 승인할 수 있다.

## 적용 범위와 현재 경계

| 자료 | 현재 위치 | 삭제·보존 시 확인할 곳 |
| --- | --- | --- |
| 상담 신청의 성명·기관명, 전화번호, 분야, 내용 | `CONTACT_INTAKE_ENABLED=true`일 때만 `api/contact.js`가 Resend로 메일 발송; 앱 DB에는 저장하지 않음 | Resend 발송 기록, 수신 메일함과 복사·전달본, 운영자 기기 및 관련 백업 |
| 조직·사업장·회원·계정 | Supabase Auth 및 `organizations`, `organization_members`, `companies` 등 | 계정과 회원 관계, 조직에 연결된 업무 자료와 인증 로그 |
| 거래·증빙·검토·감사 | `transactions`, `evidence_files`, `audit_logs`, private Storage `transaction-evidence-private` | DB 메타데이터와 Storage 객체를 각각 확인; 승인·감사 기록의 법적 보존 여부 별도 판정 |
| 직원·급여·4대보험 | `employees`, `private.employee_identity_secrets`, `payroll_periods`, `payroll_entries`, `insurance_requests`, `insurance_request_details` 등 | 식별정보와 급여·신고 자료의 업무별 보존 근거, 참조·삭제 제약 확인 |
| 이메일 수집 기반 | intake 테이블과 private Storage `email-intake-private`; 실제 수집 비활성 | 활성화 전 원본 메일·첨부·파생 데이터·중복 제거 키의 삭제 정책 승인 |

샌드박스 테스트 자료도 위 범위에 포함한다. 테스트 자료에 실제 주민번호·계좌번호·건강정보·인증서·비밀번호를 넣지 않는다. `contact.html`은 민감정보 입력 금지를 안내하지만 자유 입력 내용을 서버가 완전히 걸러내는 것은 아니므로 상담 메일에도 실제 고객 자료를 보내지 않도록 운영한다.

## 보존기간 결정과 통제

1. 각 자료군의 수집 목적, 처리 역할(위탁 여부 포함), 법적 근거, 보존 시작일과 종료일, 예외적인 법정 보존 의무, 정보주체 고지 문구를 책임자가 표로 확정한다. **현재 일괄 보존기간은 미확정**이다. 근거 없이 임의 기간을 코드에 넣거나 자동 삭제를 켜지 않는다.
2. 목적이 끝나거나 확정한 기간이 지나면 지체 없이 파기한다. 다른 법령으로 보존해야 할 자료는 근거·범위·종료일을 기록하고 업무 데이터와 분리해 접근을 제한한다. 분쟁·감사 보존 요청도 근거와 해제 조건을 기록한다.
3. 정보주체의 열람·정정·삭제 요청은 접수 시각, 요청자 확인, 대상 조직/사업장, 담당자, 법정 보존 예외, 처리 결과와 통지 시각을 기록한다. 권한 없는 조직 데이터는 조회하지 않는다. 삭제 요청을 받았다고 곧바로 모든 참조 레코드를 일괄 삭제하지 않는다.
4. 공개 개인정보 처리방침과 상담 동의 문구에는 확정된 자료별 보존기간, 파기 절차, 수탁자/국외 처리 여부, 담당 연락처를 반영한다. 현재 상담 폼의 “전화로 확인” 문구는 운영 승인 전 임시 상태이며, 온라인 상담은 기본 차단이다. 운영 책임자가 문구와 메일 보존·삭제 절차를 확인한 뒤에만 Vercel의 `CONTACT_INTAKE_ENABLED=true`를 설정한다. Preview/Production 환경을 각각 확인한다.

### 파기 실행 순서 (승인된 기간·대상에 한함)

1. 담당자가 조직/사업장과 자료 범위를 확인하고 대상 행·Storage 객체·외부 메일/발송 기록 목록을 만든다. 다른 조직의 자료가 포함되지 않았는지 두 번째 검토자가 확인한다.
2. 보존 예외 및 참조 관계를 확인한다. 감사 기록에는 필요한 최소 사건 정보만 남기고, 불필요한 원문·식별자를 제거한다. 삭제 작업의 요청·승인·시각·수량·오류를 민감정보 없는 별도 작업 기록에 남긴다.
3. private Storage의 실제 객체를 Storage API로 삭제하고 결과를 확인한 뒤 연관 DB 메타데이터를 삭제한다. 어느 한쪽에서 실패하면 성공으로 표시하지 않고 재시도/수동 조사를 연다. SQL에서 `storage.objects`만 지우거나 버킷을 공개 전환하지 않는다.
4. Auth 계정, DB 행, 메일함·Resend·다운로드/전달본 등 해당 처리 위치의 삭제를 각각 수행한다. 삭제 전후 권한 없는 계정으로 접근 불가를 확인한다. 백업은 별도 만료 주기에 따라 소멸하며, 복구 때 과거 삭제 대상이 재등장하지 않도록 삭제 목록을 재적용하고 재확인한다.
5. 전자적 파일은 복구할 수 없도록 삭제하고, 종이 출력물이 있다면 분쇄 또는 소각한다. 완료 증적에는 원본 개인정보나 비밀키를 붙이지 않는다.

**현재 상태:** 범위 추출, 예외 판정, 다중 저장소 삭제, 백업 복구 후 재파기를 자동화한 관리자 도구와 실제 삭제 리허설은 없다. 수동 절차를 마련해도 실제 고객 데이터 반입 게이트는 통과하지 않는다.

## 백업 계획 (Supabase Free 요금제)

Supabase 무료 요금제에서 다운로드 가능한 관리형 일일 백업/PITR을 전제로 하지 않는다. 운영 책임자는 승인된 비밀관리 수단으로 DB 접속 정보를 보관하고, 검증된 CLI의 `supabase db dump`를 이용해 정기적으로 내보내는 절차를 구축한다. 덤프에는 개인·급여정보가 포함되므로 로컬 개인 기기나 저장소에 평문으로 두지 않는다. 암호화된 별도 보관 위치, 최소 권한, 접근 기록, 보관 만료·삭제, 실행 실패 알림을 먼저 정한다.

DB 덤프에는 Storage 파일 내용이 포함되지 않는다. 두 private 버킷의 객체는 권한을 제한한 별도 내보내기와 무결성 목록(객체 경로·크기·체크섬·백업 시각)을 마련해야 한다. Auth/DB와 Storage의 복원 시점 차이, 메일 제공자의 자체 보관은 따로 다룬다. 인증 비밀·service-role 키를 덤프나 저장소에 기록하지 않는다. **현재 자동 백업 스케줄, 외부 보관소, 실패 알림, 복원 시점 목표는 미구축**이다.

운영 승인 전 담당자는 백업 빈도·보관기간·복구 시점 목표(RPO)·복구 소요 목표(RTO)를 실제 업무와 법정 보존 의무에 맞춰 기입하고 책임자 승인을 받는다. 무료 프로젝트의 비활성 일시중지도 가용성 계획에 반영한다.

## 복원 연습과 장애 대응

1. 실제 서비스가 아닌 격리된 환경에 승인된 백업을 복원한다. 최소 두 조직의 테스트 자료로 행 수와 참조 무결성, Auth 연계, RLS 교차 접근 거부, private Storage 객체의 존재·무결성과 다운로드 권한, 파기 목록 재적용을 확인한다. 테스트 후 격리 환경과 복사본을 정해진 기간 안에 제거한다.
2. 접속 장애·백업 실패·자료 불일치·무단 접근 의심을 발견하면 쓰기/업로드/신고 기능을 우선 차단하고 시각·영향 조직·증상을 개인정보 없는 사건 기록에 남긴다. 책임자가 원인을 확인해 접근키 회전과 세션 차단, 백업 무결성 확인, 복원 여부를 결정한다.
3. 복원 후 자료 누락·중복, Storage 불일치, 조직 간 접근, 승인 상태, 삭제 요청의 재등장을 점검한다. 업무 담당자가 결과를 승인하기 전 실제 기관 신고와 자동 처리를 재개하지 않는다. 개인정보 침해가 의심되면 관련 법령에 따른 신고·통지 여부와 기한을 담당자가 즉시 판정한다.

**실습 증적 양식:** 실행일 / 실행자·검토자 / 백업 생성 시각 / 복원 대상 / DB·Storage 검증 결과 / 두 조직 격리 결과 / 삭제 목록 재적용 결과 / RPO·RTO 측정 / 실패·재시도 / 승인. 비밀·개인정보 원문을 증적에 넣지 않는다. 아직 수행된 실습은 없다.

## 실제 고객 데이터 반입 전 완료 조건

- [ ] 자료군별 법적 보존기간·처리 근거, 책임자, 개인정보 처리방침/상담 동의 문구와 외부 수탁 처리를 확정
- [ ] DB·Storage·메일·기기별 삭제 경로와 법정 보존 예외를 테스트 자료로 검증
- [ ] 암호화된 별도 DB 및 Storage 백업, 접근통제·만료·실패 알림을 구현하고 성공 증적 확보
- [ ] 격리 복원 연습에서 Auth/DB/Storage 일치, 두 조직 RLS, 삭제 재적용, RPO/RTO를 측정
- [ ] 침해/장애 연락 책임자와 신고·통지 판단 절차, 복구 승인자를 지정
- [ ] `docs/SECURITY.md`의 다른 게이트와 Issue #2 잔여 조건도 충족
